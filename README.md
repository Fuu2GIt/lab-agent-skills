# lab-agent-skills

研究室の学生それぞれのエージェントが、GitHub Project のボード管理と TODO（Issue）作成を同じやり方で回すためのスキル集です。

## 入っているスキル

| スキル | 場所 | 何をするか |
| --- | --- | --- |
| `lab-todo-create` | `lab-todo-create/SKILL.md` | 学生と1問ずつ確認しながら Issue（TODO）を作る。議事録からの Issue 化、Issue の分割、質問票の作成も扱う |
| `lab-board-manage` | `lab-board-manage/SKILL.md` | ボードの優先順位の提案、`担当中` への移動、完了の確認とクローズ、`未定` の再確認を行う |

2つは別々のスキルです。エージェントは、学生の依頼内容に合うほうを説明文（description）から選びます。

## 使い方

1. 学生本人が、このリポジトリから使いたい `SKILL.md` を自分のエージェントに読み込ませます。読み込み方は、使っているツール（Grok Bot、Cursor など）の方法に従ってください。
2. 学生がエージェントに話しかけます。例：「Issue を作りたい」「ボードの優先順位を見て」「この議事録から Issue を作って」。
3. エージェントは、わからないことを1問ずつ、推奨回答つきで学生に聞きます。学生の答えが出そろうまで、思い込みでは進めません。

## 共通の約束

- 操作するのは、学生が参加しているテーマのボードと、そのテーマのリポジトリ、学生本人の小研究リポジトリだけです。`lab-hub` と `lab-knowledge` は読むだけです。
- Issue の作成や分割、ラベルや担当者の設定、ボードへの追加、`担当中` への移動、クローズ、優先順位の番号の付け直しは、学生が「はい」と言ってから行います。
- 質問票（`notes/questionnaire.md`、複数人のテーマは `meetings/questionnaire.md`）の追加や更新は、学生が「はい」と言ってから Draft PR で出します。`main` には直接 push しません。
- Issue のタイトルは `番号. [接頭辞] 内容` の形です。番号は優先順位（1が最優先）で、締め切りは書きません。

## 注意

- スキルの本文は英語で書かれています。エージェントは学生と日本語で話します。
- 研究室の方針（`lab-hub` の policy）が変わったときは、このスキルも直してください。

## スキルの中身（日本語の説明）

`SKILL.md` は英語で書かれています。ここでは、その内容を日本語でまとめます。

### 2つのスキルに共通すること

- 聞き方：エージェントは学生に1問ずつ、推奨回答つきで聞きます。調べればわかること（リポジトリ、議事録、既存の Issue、ラベル、会話の履歴）は、聞かずに自分で調べます。学生が言っていない抜けやリスクは、エージェントから挙げて聞きます。学生の返事が引用だけだったり意味があいまいだったりするときは、思い込まずに確認します。
- 質問票：質問と学生の答えは、チャットで聞きながら、質問の数に関係なく1つのファイルにも残します。新しい質問は同じファイルの末尾に足します。学生1人分は `notes/questionnaire.md`、テーマで2人以上が答える分は `meetings/questionnaire.md` です。件名（Issue）ごとに、`## 件名: ...（Issue #番号 関連、作成日 YYYY-MM-DD）`、`### 決めたいこと`、`### すでに分かっていること`、`### 回答欄` の見出しで分けます。聞き始める前に既存の質問票を読み、答えが出ている項目は聞き直しません。追加や更新は、学生が「はい」と言ってから、ブランチを切って Draft PR で出します。
- 食い違い：チャットの答えと質問票が食い違うときは、新しいほうを正しいとして学生に確認し、「はい」をもらってから Draft PR でファイルを直します。学生がファイルを直接直したときは、ファイルの内容を正しいとします。
- 読む・提案する・聞くだけなら、確認なしで進めます。Issue やボードを変える操作は、案を見せて「はい」をもらってから行います。
- 聞き終わりの条件：全項目に答えが出ているか「関係なし」と確認され、決まったことに矛盾がないことです。最後に「他に気になることは？」を1回だけ聞きます。

### lab-todo-create（TODO・Issue を作る）

使う場面：議事録や学生の言葉から Issue を作るとき、大きな Issue を分けるとき、ラベル・番号・先に終わらせるもの・`未定` を整えるとき、小研究リポジトリの Issue をボードに載せるときです。優先順位、`担当中` への移動、クローズは `lab-board-manage` の担当です。

聞く順番は、上流から次のとおりです。

1. 対象を決める：どのテーマのリポジトリか、どの小研究リポジトリか、何から作るか（議事録、学生の言葉、既存 Issue の分割）。見えないボードやアクセスできないリポジトリは探し回らず、学生に伝えます。
2. 材料を読む：学生が指定した議事録を読み、既存の Issue やボードを見て重複や前提になりそうな Issue を探します。議事録から候補を並べ、「この N 件を Issue にしますか？」と聞きます。学生が指定していない議事録は、自分で読みに行きません。
3. Issue の中身を決める：1つの Issue は1つの目的にします。目的が複数ならあとの「分割」を提案します。完了条件と確認方法は、作るたびに「今書くか、`担当中` にする前に書くか」を聞きます（推奨は、Todo の段階では目的と背景だけ書き、`担当中` にする前に書くこと）。
4. エージェントが自分で決める項目：目的別ラベル（`spike`、`task`、`feature`、`bug` のうち一番近いもの）、エージェント用ラベル（`human-only`、`agent-ok`、`needs-split`、`needs-clarification`。リポジトリに既にあるときだけ付け、無断で作らない）、先に終わらせる Issue と終わったら始められる Issue の番号です。決めた内容は提案に入れて学生が直せるようにし、決められないときだけ1問聞きます。
5. 残った疑問と `未定`：疑問は Issue に書かず、その場で学生に聞き、「その疑問を解くタスクも追加しますか？」と聞きます。「〜を決める」という名前のタスクは作りません。決められないときは、決まらないと進めない後続の Issue の本文に `未定：〜（#番号 が終わったら再確認）` と1行書きます。
6. 優先順位の番号：タイトルの先頭の番号で表します（1が最優先）。理由は、簡潔でわかりやすく、なぜその優先度なのかまで書き、締め切りは書きません。既存 Issue の番号の付け直しは「はい」をもらってからです。
7. 分割：分割案（子 Issue は1つの目的）を見せ、「はい」をもらってから子 Issue を作り、GitHub のサブ Issue で親子をつなぎます。
8. ボードへの追加：テーマのリポジトリの Issue は自動で載るので聞きません。小研究リポジトリの Issue は自動では載らないので、「ボードにも載せますか？」と聞き、「はい」をもらってから載せます。
9. 考慮すべきこと：同じ内容の Issue が既にないか、担当者が学生本人か、先に終わらせるものと後続が逆になっていないか、番号が循環していないか、成果物の場所（パスやリンク）が決まっているかを、エージェントから確認します。

作るときの決まり：

- タイトルは `番号. [接頭辞] 内容` です。接頭辞は `[調査]`、`[タスク]`、`[機能]` で、bug には接頭辞がないので `[タスク]` を使います。
- 本文は、目的、背景、完了条件、確認方法、参考資料、先に終わらせるもの、終わったら始められるもの、未定（あるときだけ）の順です。
- 完了条件の目安：`spike` は「できる／できない／条件つきでできる」のどれかと根拠、`task` は成果物の場所、`feature` は PR がマージされて確認方法どおりに動くこと、`bug` は再現手順で再現しなくなることです。
- 担当者は学生本人です（エージェントは学生のアカウントで動きます）。
- 作ったあとは、番号とタイトルを学生に報告します。小研究リポジトリの場合は、ボードに載せたかどうかも伝えます。

### lab-board-manage（ボードを管理する）

使う場面：「今日、何から手をつける？」と聞かれたとき、「これを始める」と言われたとき、「終わった」と言われたとき、先に終わらせる Issue が終わって後続の `未定` を聞き直すときです。新しい Issue を作る、分ける、議事録から Issue にするのは `lab-todo-create` の担当です。

聞く順番は、上流から次のとおりです。

1. 対象を決める：学生が参加しているテーマのボードと、そのテーマのリポジトリ、学生本人の小研究リポジトリだけを操作します。研究室全体のハブのリポジトリと知識のリポジトリは読むだけで、変えたいときはそのリポジトリに Issue で提案します。
2. 優先順位の提案：学生が指定した範囲（指定がなければ `Todo` 列全体と学生に割り当てられた Issue）を読みます。優先順位は、タイトルの先頭の番号で表し（`1. [タスク] 内容` の形）、番号ごとに1行の理由（なぜその優先度か）をつけます。締め切りは書きません。「今日やる／後でいい／相談したい」の3分類は使いません。提案を見せ、学生が決めたら「タイトルの番号を付け直してよいですか？」と聞き、「はい」で付け直します。`human-only` の Issue は始める候補にせず、触りません。
3. `担当中` への移動（学生が「始める」と言ったとき）：次の3つが全部そろっているか確認します。足りないものはその場で聞いて決めます。(1) 担当者が学生本人である（担当者がいないまま、または他の人が担当のまま移さない）。(2) 完了条件と確認方法が書かれている。(3) `未定` が残っていない。そろったら移動の案を見せ、「はい」をもらってから移します。
4. 完了の確認とクローズ：「終わりましたか？」と聞くのは、学生が「終わった」と言ったとき、完了条件を満たす作業がチャットで確認できたとき、その Issue にひもづく PR がマージされたときだけです。エージェントが「終わっていそう」と思っただけでは聞きません。「はい」をもらったら、結果を1行でコメントし、Issue をクローズします（クローズするとボードで自動的に `Done` に移ります）。
5. `未定` の聞き直し：クローズした Issue の「終わったら始められるもの」に書かれた Issue を探し、その `未定` を学生にもう一度聞きます。決まったら、`未定` の行を決まった内容に書き換える案を見せ、「はい」で直します。まだ決まらなければ `未定` のまま残し、前提の Issue が終わるたびに聞き直します。
6. 考慮すべきこと：担当者がいない、または他の人が担当の Issue は触らない。番号の付け直しはたくさんの Issue のタイトルを変えるので、件数を見せてから「はい」をもらう。担当者を勝手に変えない。`Todo` に担当者つきの未着手カードがあるときは、作業を始めたかを学生に確認する。卒業や引き継ぎで `担当中` のまま残っている Issue は、閉じるか引き継ぐ（担当者を変える）かを確認する。

### やらないこと（2つのスキルに共通）

- 学生の「はい」をもらう前に、Issue の作成や分割、ラベルや担当者の追加、ボードへの追加、`担当中` への移動、クローズ、番号の付け直しをしません。
- 足りない情報を推測で埋めません。聞きます。
- 「〜を決める」という名前のタスクを作りません。
- 質問票を、学生の「はい」の前に作りません。質問票のファイルを `main` に直接 push しません。
- 優先順位の理由に締め切りを書きません。
- 研究室全体のハブのリポジトリと知識のリポジトリには書き込みません。
- 学生が参加していないテーマのボードやリポジトリ、アクセスできないものは操作しません。
- `main` に直接 push しません。ファイルを変えるときは、ブランチと Draft PR を使います。
- 研究以外の作業（事務、行事など）は対象外です。

`lab-todo-create` だけ、さらに次を守ります。

- 担当者を空にしません。他の人に割り当てられた Issue を自分で引き受けません。
- エージェント用ラベルを、許可なく作りません。

`lab-board-manage` だけ、さらに次を守ります。

- 担当者がいないまま `担当中` に移しません。
- 「Todo から好きなものをやって」のような指示で、全部を自分から始めません。
- `human-only` の Issue に触りません。
